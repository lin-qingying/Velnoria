# 清洁实现流程

目标：使每一行代码都能追溯到公开规格或外部可观测行为，而不是某个反编译产物。
本文件约束"怎么得到知识"，不是法律意见。公开发布前仍需外部评审。

## 1. 允许的知识来源

| 来源 | 允许 | 说明 |
|---|---|---|
| 公开协议文档（wiki.vg 等） | 是 | 直接依据 |
| 原版服务端的可观测输出 | 是 | 保留下载的字节/存档作为证据 |
| 差分测试结果 | 是 | 本项目主要依据 |
| 官方数据生成器输出的结构化数据 | 有条件 | 只能作为数据，不得反推代码结构 |
| 客户端 jar 的资源文件（语言、模型） | 有条件 | 只作颜色与结构参考，重制为自有资产 |
| 反编译源码 | 仅阅读 | 不复制、不翻译、不逐行派生；不得参与对应模块的实现 |

判定红线：如果一段代码的**结构**（函数拆分、命名、分支顺序）能对应到某个反编译产物，即视为派生。重写时以规格文档为准，不参照源码组织。

## 2. 规格先行

每个模块在实现前必须提交规格文档到 `docs/protocol/` 或 `docs/design/`，包含：

1. 该模块的可观测行为（输入 → 输出）
2. 依据来源（链接、抓包夹具编号、数据导出文件名）
3. 边界条件与错误处理
4. 验收方式与所属一致性级别（见 `docs/parity/levels.md`）

规格提交时间必须早于实现提交时间，由 git 历史与工作记录共同证明。

## 3. 分工（如有协作者）

- **Reader**：可以阅读反编译源码，只产出规格与夹具，不得提交 `core/`、`ue/` 的实现代码。
- **Writer**：只读规格与夹具，不接触反编译源码，负责实现。
- 单人项目时同一人兼任两角色，则必须在工作记录中标记"本模块参照过源码"，该模块默认不允许外部贡献者改动。

## 4. 记录要求

所有工作按 `AGENT.md` 记入 `docs/worklog/`。属于清洁实现证据的最小集合：

| 字段 | 内容 |
|---|---|
| 模块 | 受影响的子系统 |
| 知识来源 | 使用的文档、夹具编号、导出文件 |
| 是否接触反编译源码 | 是/否 |
| 规格文档提交 | 提交哈希 |
| 验证方式 | 用例名与结果 |

## 5. 污染处置

1. 发现某模块实现与反编译产物结构相似 → 停止合并，标记 `contaminated`。
2. 由未接触源码的一方按规格重写，旧实现删除而非改写（保留在 git 历史中并记录原因）。
3. 记录写入 `docs/worklog/`，并在 `docs/parity/diffs/` 关联受影响用例。

## 6. DMCA / 投诉应对

- 定位：投诉指向的文件 → `git log` → 对应用户故事与规格文档。
- 响应：先下架争议内容，再提交清洁实现记录（规格提交时间、来源清单、验证结果）。
- 不改写历史。记录本身就是抗辩材料。
