| 项目 | 内容 |
|---|---|
| 名称 | Lumenvox（待商标与域名检查） |
| 性质 | 个人开源项目，非商业 |
| 许可 | GPL-3.0 |
| 目标 | 以清洁实现方式，完整重写 Java 版 26.3 的客户端与游戏逻辑，使用 Unreal Engine 提供真实光影，与原版行为做差分对照 |
| 目标版本 | Java 版 26.3，协议号以用户本机服务端 jar 的 `version.json` 为准 |

## 1. 目标与非目标

**目标**
- 单机游戏：创建、打开、保存世界，与原版存档互通。
- 多人游戏：连接原版服务器（离线与正版在线模式），并支持 LAN。
- 游戏逻辑：世界生成、光照、实体、AI、合成、熔炉、附魔、药水、红石、流体、活塞、命令与聊天，行为与原版一致，并以差分测试验证。
- 表现：UE 渲染，支持 PBR 材质、Lumen 全局光照、透明与折射处理。
- 用户自备正版游戏文件，运行时读取，项目不分发任何 Mojang 或 Microsoft 资产。

**非目标**
- 不做模组 API 的兼容层（核心稳定后再考虑原生扩展接口）。
- 不做商业发行、内购或订阅。
- 不做 Bedrock 版兼容。
- 不替代或复刻 Mojang 的服务端基础设施（领域、账号、皮肤服务）。

                │
┌───────────────┴─────────────────────────────────┐

┌───────────────┴─────────────────────────────────┐

│ launcher（检测与引导）、tools（抓包、录制、比对）         │
└─────────────────────────────────────────────────┘

**运行模式**
- **集成服务端**：单机与 LAN 主机共用同一套 `sim`、`world`、`gen`，客户端通过内存通道与之通信，不经网络。
- **远程服务器**：客户端通过 `protocol` 连接任意原版或兼容服务器。
- 两种模式共享客户端的渲染与输入路径。

**线程模型**
- 网络线程：收发、加解密、解压。
- 模拟线程：固定 20 TPS，驱动 `sim`。
- 生成线程池：地形生成与光照计算。
- 网格线程池：区块网格化，产出结果交主线程提交。
- 主线程：UE 游戏线程，只做提交与状态同步。
- UE 渲染线程：只消费快照，不做游戏判断。

**数据流原则**
- 核心层是唯一的游戏状态权威，UE 只读取快照。
- 输入由 UE 采集后转换为动作事件，发送给核心层，不直接修改状态。
- 所有跨线程数据使用不可变快照或无锁队列，避免共享可变状态。

## 4. 核心子系统

### 4.1 协议（protocol）
- 覆盖所有连接状态：Handshake、Status、Login、Configuration、Play。
- 帧格式：VarInt 长度前缀、zlib 压缩、压缩阈值。
- 加密：AES/CFB8 流加密，配合 RSA 密钥交换，用于在线模式。
- 基础类型：VarInt、VarLong、String、UUID、Position、Angle、ID set、可选值、数组。
- NBT：GZIP 与无压缩两种形式，用于注册表与文本组件，解码设上限防止内存放大。
- 包定义：每个协议版本一份包表，未识别的包保留原始字节。
- 版本常量与包 ID 由 `prepare` 从服务端 jar 读取并校验。
- 解码失败返回错误，不 panic；长度超限直接拒绝。

### 4.2 认证（auth）
- **离线模式**：UUID 按 `UUIDv3("OfflinePlayer:" + name)` 生成，与原版逐一比对。
- **正版模式**：微软账号登录，经 Xbox Live 与 XSTS 换取 Minecraft 服务令牌，获取档案。
- **会话验证**：进入在线服务器时，执行会话哈希、加入请求与服务端校验流程。
- 令牌存入系统凭据管理器（Windows Credential Manager、macOS Keychain、Linux Secret Service），不明文保存。
- 认证流程只在用户主动操作时发起，不做后台轮询。

### 4.3 世界数据（world）
- 区块结构：章节（section）、调色板容器、方块状态、群系调色板。
- 光照数据：天光与方块光各 4 位，按章节存储。
- 存档：Anvil 区域文件（`.mca`）的读写，与原版格式互通。
- 区块与实体的 NBT 数据读写，保留未知字段，保证往返不丢数据。
- 存档升级：读取旧版数据版本时执行与原版一致的数据修正。
- 区块加载与卸载由视距驱动，缓存策略按访问频率调整。

### 4.4 注册表（registry）
- 方块、方块状态、物品、实体类型、群系、标签、配方、战利品表、进度、附魔、药水等全部由 `prepare` 导出的数据驱动，不手写。
- 运行时只读，启动时校验版本哈希。
- 数据来源：服务端 jar 的数据生成器输出，与客户端 jar 的资源文件（语言、模型、blockstate）。

### 4.5 世界生成（gen）
- 实现密度函数、噪声采样、群系映射、表面规则与结构放置，遵循原版的数据驱动生成管线。
- 种子处理与随机源与原版一致，同种子同坐标输出必须与原版相同。
- 结构（村庄、神庙、要塞等）的放置规则按数据文件执行，不写死位置。
- 生成顺序与区块边界处理需与原版一致，避免接缝差异。

### 4.6 光照（light）
- 天光与方块光的传播算法与原版逐格一致，包括区块边界、透明方块、遮挡与衰减。
- 方块变化时的增量更新，与原版的更新顺序一致。
- 光照结果同时供给 `sim`（生成刷怪判定）与 `render`（烘焙与材质输入）。

### 4.7 模拟（sim）
- 固定 20 TPS，tick 顺序与原版一致。
- **实体系统**：采用 ECS 结构，组件包括位置、速度、碰撞箱、属性、AI 目标、状态效果、库存等。
- **AI**：目标选择器、寻路、行为树或等效的目标优先级，与原版行为对齐。
- **战斗**：伤害计算、护甲、附魔、击退、无敌帧、食物与饥饿。
- **物品与合成**：合成表、熔炉、高炉、烟熏炉、酿造台、附魔台、铁砧、砂轮等。
- **红石**：红石粉、中继器、比较器、活塞、观察者、拉杆等的更新顺序、延迟与信号强度与原版一致。
- **流体**：水与岩浆的流动、冲突、源方块生成。
- **随机 tick**：作物生长、树苗、冰雪融化、叶子衰减等。
- **生物生成**：按光照、群系、区块随机源判定，与原版概率一致。
- **时间与天气**：日夜循环、雨雪、雷暴。

### 4.8 玩家与交互（player）
- 移动：客户端预测与服务端校正，碰撞检测与原版一致。
- 挖掘：工具效率、附魔、硬度计算、挖掘进度包。
- 放置：方块状态推断、朝向、放置校验。
- 容器：背包、箱子、熔炉等的槽位操作、点击模式与同步。
- 饥饿、呼吸、摔落、游泳、飞行等玩家状态。

### 4.9 文本与命令（text）
- 文本组件解析与渲染，包括颜色、格式、点击与悬停事件。
- 命令系统：解析树、补全、权限等级，与原版命令树对齐。
- 聊天：签名、消息链、过滤（在线模式）。
- 语言文件由用户本机资源提供，支持切换语言。

### 4.10 渲染（render，UE 插件）
- **区块网格化**：自定义贪心网格化，在生成线程池完成，主线程只做提交。
- **材质**：每个方块的 PBR 参数由项目制作，原版纹理只作颜色参考。
- **透明与折射**：水、玻璃、冰、史莱姆方块等使用独立的半透明通道，处理排序与折射。
- **光照**：天光映射到 Sky Atmosphere 与 Directional Light；方块光烘焙为 3D 体积纹理，发光方块配合 emissive 材质参与 Lumen 间接光照。
- **实体渲染**：实体模型由 `prepare` 转换，骨骼动画与姿态与原版一致。
- **粒子与天气**：使用 UE Niagara 实现，参数与原版对齐。
- **画质档位**：提供多档设置，允许关闭 Lumen 回退到预烘焙光照。
- **渲染距离**：可配置，默认 8–12 区块，优先保证帧率稳定。

### 4.11 音频
- 音效与音乐由 `prepare` 从用户本机资源转换为 UE 可用格式。
- 3D 空间音效、衰减、混响随环境变化。
- 音效事件与原版的触发时机一致。

### 4.12 输入与相机
- 键位映射可配置，与原版默认键位兼容。
- 第一人称与第三人称视角，视角平滑与灵敏度可调。
- 手柄支持作为可选项。

### 4.13 单机与内置服务端
- 创建世界、加载存档、保存、退出，与原版流程对齐。
- 内置服务端使用与远程服务器相同的 `sim`，保证单机与多人行为一致。
- 支持打开 LAN，供局域网内其他客户端连接。

### 4.14 设置与资源包
- 用户资源包：读取符合格式的资源包，覆盖纹理、语言、音效。
- 设置项：画质、音量、键位、语言、渲染距离、界面缩放。
- 配置文件使用 TOML 或 JSON，存于用户配置目录。

## 5. 数据管线（prepare）

1. **检测**：定位官方安装目录，读取 `versions/26.3/26.3.json`，找到客户端与服务端 jar。
2. **校验**：比对 jar 的哈希与清单版本，不一致则拒绝继续。
3. **导出**：调用服务端 jar 的数据生成器，输出注册表、标签、配方、战利品表、结构、群系、噪声与生成规则等。
4. **提取**：从客户端 jar 提取 blockstate、模型、纹理（颜色参考）、语言文件、音效与实体模型。
5. **转换**：生成项目自有的二进制格式，写入用户本地应用数据目录。
6. **缓存管理**：记录版本、哈希与生成时间，支持增量更新与清理。

约束：
- 缓存只存在用户机器上，不分发。
- 每个游戏版本单独缓存，升级版本需要重新准备并重跑差分测试。

**本机实施事实**（详见 `docs/environment.md`）：
- 目标安装：`D:\GAMES\.minecraft\versions\26.3-Fabric`，客户端 jar sha1 已校验，与官方清单一致，Fabric 补丁不在该 jar 内。
- 服务端 jar 缺失，第 3 步"调用服务端 jar 的数据生成器"当前无法执行，S0 门禁阻塞。处置方案待定（用户自备 / 启动器引导 / 不依赖服务端），未定稿前不进入实现。

## 6. 启动器（launcher）

- 检测本机是否已安装 UE 5.x 与对应版本。
- 未安装时打开 Epic 官方下载页或唤起 Epic Games Launcher，由用户自行登录与安装。
- 检测本机是否已安装正版 Java 版 26.3；未安装时提示用户通过官方启动器安装。
- 运行 `prepare`，显示进度，缓存完成后启动客户端。
- 不接触 Epic 账号或 Microsoft 账号的密码；正版登录只在客户端内进行。
- 不下载、不托管、不代理任何 UE 或 Minecraft 文件。

## 7. 测试与验证

### 7.1 差分测试（主要手段）

| 模块 | 基准 | 方法 |
|---|---|---|
| 协议 | 原版服务端与客户端抓包 | 解码再编码，逐字节比对 |
| 认证 | 原版客户端的登录流程 | 比对请求与响应字段 |
| 区块与存档 | 原版服务端下发与保存的区块 | 逐方块、逐调色板比对 |
| 光照 | 原版光照值 | 逐格比对，重点测试区块边界与透明方块 |
| 世界生成 | 原版生成的区块 | 同种子逐方块比对 |
| 注册表与标签 | 服务端数据生成器输出 | 结构比对 |
| 实体与 AI | 录制的原版 tick 状态 | 逐 tick 比对位置、状态、目标 |
| 红石与流体 | 录制的原版更新序列 | 逐 tick 比对方块状态变化 |
| 合成与配方 | 原版配方输出 | 穷举输入组合比对输出 |
| 命令与文本 | 原版命令树与输出 | 比对解析结果与格式化文本 |

差分测试不通过的功能不合并。测试结果与夹具的生成方法公开发布。

### 7.2 其他测试
- **属性测试**：编解码往返、NBT 往返、调色板压缩等。
- **模糊测试**：协议解码、NBT 解析、存档读取，防止崩溃与内存问题。
- **性能基准**：tick 耗时、区块生成耗时、网格化耗时、帧时间，与原版对比记录。
- **视觉对照**：同一场景的 UE 渲染与原版截图对照，记录差异并分类。
- **压力测试**：长时间运行、大量实体、频繁区块加载卸载。

### 7.3 夹具管理
- 夹具存于 `tests/differential/fixtures/26.3/`，只存协议字节与状态记录，不含原版素材。
- 若发布前对夹具的版权性存疑，改为本地生成，仓库不包含夹具。

## 8. 构建、CI 与发布

| 认证服务变化 | 认证模块独立，接口变更时只改该模块 |
| 个人项目的工作量 | 工作量极大，见第 11 节 |

## 11. 资源与现实评估

本方案覆盖 Java 版的完整游戏逻辑与客户端，这是多年规模的工程。Horizon 作为参照，三至四周提交数千次，并依赖大量 AI 代理完成编码，但它的目标是完整对等，并且仍存在玩家可见的差异。

对个人项目，应接受以下现实：
- 完整对等需要的时间远超单人的常规项目周期。
- 差分测试的基础设施本身就需要大量投入。
- 光影与 UE 集成的美术工作量与技术工作量相当。
- 版本更新会周期性地消耗相当比例的精力。

本文档不排定时间表。工作顺序与取舍属于实施阶段的决定，不在本方案范围内。

## 12. 待决策事项

1. **实现语言**：核心层用 C++，与 UE 表现层统一；或用 Rust 实现核心，通过 C ABI 与 UE 对接。
2. **夹具是否入库**：入库便于复现，但需先评估版权风险。
3. **光影默认档位**：默认开启 Lumen，还是默认预烘焙。
4. **名称确认**：Lumenvox 是否通过商标与域名检查。
5. **认证与协作**：是否计划协作者，决定清洁实现的分工方式。
6. **数据版本范围**：是否只支持 26.3，还是为后续版本预留适配结构。

以上事项确认后，本方案可以直接作为实施依据。
