# 一致性分级（Parity Levels）

本文件定义 Velnoria 对原版 26.3 的"一致"到底指什么、如何判定、哪些差异被允许。
它是工作量分配与 CI 门禁的依据，优先于任何模块自行判断。

总纲要"行为与原版一致"，但不同子系统的"一致"在工程上不是一回事：
协议错一个字节就连不上服务器，AI 寻路差半个方块玩家不会察觉。
把两者按同一标准验收，结果是差分测试长期红灯、门禁失效。

## 1. 五个级别

| 级别 | 名称 | 定义 | 判定手段 | 允许差异 |
|---|---|---|---|---|
| P0 | 字节一致 | 编解码、序列化格式必须与原始字节完全相同 | 解码→再编码，逐字节比对 | 无 |
| P1 | 状态一致 | 给定相同输入，最终状态与原版完全相同 | 同种子/同输入逐格、逐 tick 比对 | 无 |
| P2 | 统计一致 | 随机过程的结果分布与原版相同；记录场景可复现 | 分布检验 + 录制序列回归 | 单次结果可不同 |
| P3 | 观感一致 | 视觉/听觉传达相同信息，允许刻意增强 | 截图对照 + 人工评审 | 有意增强的部分 |
| P4 | 不承诺 | 不作为兼容性指标 | 仅记录 | 全部 |

### P0 字节一致

判据不是"看起来对"，而是往返不变式：

- `decode(bytes) → encode() == bytes`（对已规范化的字段集）
- 原版写入 → 我方读写 → 原版读取，数据无损；我方再写一次，字节不变
- 未知字段必须原样保留（NBT 未知 tag、包内未知尾部字节）

覆盖：VarInt/VarLong/UUID/Position/NBT（GZIP 与裸）、每状态包表、压缩阈值以上/以下的帧、Anvil 区域文件、区块调色板、实体 NBT、文本组件的 JSON/NBT 两种形态。

任一 P0 用例失败即阻断合并，无豁免通道。豁免只能通过修改本文件实现，改文件需在 PR 说明理由。

### P1 状态一致

给定完全相同的初始条件与输入序列，我方状态快照与原版逐字段相等。

覆盖：世界生成（同种子逐方块、逐群系、逐结构起址）、光照（含区块边界、透明方块、遮挡、天空光衰减）、流体流动、红石更新顺序与延迟、方块更新顺序、容器槽位操作、玩家碰撞结果、命令解析树与文本组件渲染结果。

判据细节：
- 世界生成按"区块哈希"比对：对 N 个 (种子, 坐标) 组合，方块状态数组哈希必须全等。任何一处不等即失败，不接受"接近"。
- 光照按格点值比对，且必须比对"传播终止"而非仅最终值——终止时机不同会导致后续增量更新分歧。
- 红石与流体按 tick 序列比对：录制原版 `(tick, pos, oldState, newState)` 流，逐条匹配。

P1 用例失败阻断合并。若确认为已知不可消除差异（如原版 bug 的复刻代价不成比例），走 §3 登记为 `known-diff`，并在 CI 中转为"必须失败"用例——即断言我方确实产生该差异，防止行为漂移。

### P2 统计一致

随机过程无法逐次对齐（原版自身在不同顺序下也不同），因此比对分布而非单次。

覆盖：生物生成（类型/位置/数量的分布）、随机 tick（作物、树苗、雪、叶子）、实体 AI 目标选择、伤害随机浮动、附魔随机、战利品表抽取。

判据：
- 大样本分布检验（卡方/KS），样本量按各子系统在 `docs/parity/stats-*.md` 中固定，p 值阈值统一 0.01。
- 对录制场景（固定种子+固定输入）做逐 tick 回归，位置/目标容差在该子系统文档中显式给出，默认：位置 ≤0.01 方块，朝向 ≤0.5°。
- 容差只能收紧，不能放宽；放宽需在本文件记录并说明。

P2 失败不阻断合并，但进入日报。连续两次运行失败升级为阻断。新录制场景的首次结果作为基线，不得反向修改基线以通过。

### P3 观感一致

覆盖：区块渲染、材质、光照表现、粒子、天气、实体动画、音频混音与空间化。

判据：同一场景截图 A/B 对照 + 规格化的检查项（可辨识方块边界、透明排序无穿透、夜间可读性、天空与雾过渡连续）。光影增强是产品差异，不是缺陷。

P3 不进入自动门禁，走人工评审清单，评审记录存 `docs/parity/visual/`。

### P4 不承诺

帧率、内存占用、区块生成耗时、启动时间、加载画面时长、UE 侧崩溃恢复能力、与非原版服务器的兼容性。这些是质量目标，登记在性能基准里追踪趋势，不作为兼容性缺陷。

## 3. 差异登记表

所有非 P0 的差异必须登记，否则视为未发现缺陷。

文件：`docs/parity/diffs/<模块>.md`，每条一行：

```
| ID | 级别 | 类别 | 描述 | 触发条件 | 原版行为 | 我方行为 | 状态 | 关联用例 |
```

- `类别`：`defect`（待修）/ `known-diff`（接受，附带理由与代价评估）/ `enhancement`（刻意增强，仅 P3 允许）
- `状态`：`open` / `fixed` / `wontfix` / `accepted`
- `known-diff` 必须同时提供一条反向断言用例（断言我方确实偏离），否则状态无效
- 每个发布版本导出 `docs/parity/report-<version>.md`，汇总 open 与 accepted 条目，随发布附带

发布门槛：`defect` 状态为 open 的条目数必须为 0；`known-diff` 不限数量但需逐条列出。

## 4. CI 门禁映射

| 级别 | PR 提交 | 每日全量 | 发布 |
|---|---|---|---|
| P0 | 阻断 | 全量 | 必须全绿 |
| P1 | 阻断（子集） | 全量 | 必须全绿 |
| P2 | 不阻断，仅报告 | 全量 + 分布检验 | 无 open defect |
| P3 | 无 | 无 | 人工清单通过 |
| P4 | 无 | 趋势记录 | 附带基准对比 |

PR 子集按受影响模块选取，选取规则写在 CI 配置中，不手工指定。

## 5. 反例：什么不算"一致"

以下理由不能用于通过验收：

- "玩家看不出来"——除 P3/P4 明确覆盖范围外不成立。P1 模块的差异会在下游放大（光照→刷怪→性能）。
- "原版这里是 bug"——先复刻，再单独立项讨论是否修正，修正即为 `enhancement`，需要显式开关。
- "随机导致无法复现"——随机源与调用顺序必须与原版一致；若确实无法对齐，降级为 P2 并说明证据。
- "性能不允许"——性能属 P4，不能用来为 P1 差异开脱；实现方式可换，输出不可换。

## 6. 遗留决策

1. 各 P2 子系统的样本量与容差需在首个对应实现前定稿。
2. `known-diff` 的批准人：单人项目下由作者记录，是否引入外部评审待第 12 节第 5 项确认。
3. 夹具的版权处置（第 12 节第 2 项）会影响 §4 中"每日全量"能否在公开 CI 上运行，需与夹具策略同步定。
