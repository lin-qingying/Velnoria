## 20:31 构建链路排障（4 次失败）

- 意图：验证骨架可编译、测试可跑。
- 命令与结果：
  1. `cmake -G "Visual Studio 17 2022"` → `No CMAKE_CXX_COMPILER could be found`。指定 `-DCMAKE_GENERATOR_INSTANCE` 指向 Community 实例后仍失败。
  2. 改 NMake + `vcvars64.bat` → 链接阶段 `rc /fo ... failed: no such file or directory`，并出现安全策略阻断 `reg.exe`（不可绕过）。
  3. 改 Ninja + 手动 `INCLUDE`/`LIB`/`PATH` → 配置成功；随后暴露代码错误（见下一项）。
  4. 首次 `scripts/build.sh` → `CMake was unable to find a build program corresponding to "Ninja"`：`python -c "sysconfig.get_path('scripts')"` 返回 Windows 路径，bash 的 `[ -x ]` 判断失效。
- 失败与原因：
  - 本机两个 VS 实例均未向 CMake 注册 C++ 工具集。
  - `vcvars64.bat` 依赖注册表查询，在受限 shell 中被阻断，导致 `rc.exe` 与 SDK 路径缺失。
  - 路径风格混用（Windows 路径进入 bash 判断）。
- 修复：
  - 新增 `scripts/env-msvc.sh`：从磁盘布局推导 `INCLUDE`/`LIB`/`PATH`，不依赖注册表、不调用 `vcvars`。
  - `scripts/build.sh` 用 `cygpath -u` 转换 Python 的 scripts 目录，并显式传 `-DCMAKE_MAKE_PROGRAM`。
  - 删除已写但从未跑通的 `scripts/build-windows.bat`，避免交付未经验证的路径。
- 决策：统一 Ninja；不提供 `.bat`。理由：唯一验证通过的组合是 Ninja + 磁盘推导环境。
- 遗留：该方案仅覆盖 MSVC + Windows；Linux/macOS 构建脚本待写。

## 20:34 修复编译与测试缺陷

- 意图：让 24 个用例全绿。
- 变更：`core/include/lumenvox/core/error.hpp`、`core/src/varint.cpp`、`tests/unit/test_harness.hpp`
- 命令：`bash scripts/build.sh`
- 结果：
  - `Status::ok()` 静态工厂与 `bool ok() const` 构成非法重载（C2686），改名 `Status::success()`，同步 7 处调用。
  - `LV_CHECK_ERR` 宏对表达式求值 3 次；解码器会消费输入，导致误报与 `bad variant access`。改为 `auto&& lv_result_ = (expr)` 单次求值。
  - VarInt 判定顺序错误：第 5 字节带续位时应为 `varint_too_long`，先判载荷位宽会误报 `varint_overflow`。改为先判续位、再判位宽。
  - `getenv` 触发 C4996，为 `lumenvox_prepare` 加 `_CRT_SECURE_NO_WARNINGS`。
- 失败与原因：上述 3 类缺陷均为首轮实现自带，非环境问题。
- 决策：VarInt 采用严格解码（拒绝超长与非规范化编码），不做宽容归一化；理由是宽容解码会掩盖与真实服务端的失步。
- 遗留：属性测试、模糊测试尚未建立。
